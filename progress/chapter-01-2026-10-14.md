# Chapter 1 — 2026-10-14

**Day summary:** defined the north star and built the tooling to measure it;
production p99 is ~3 ms after removing a dead destination; the tail is
mostly queueing behind the coordinator's serial worker wakeups.

## Server survey and quick fixes

- **Why:** check the host before touching code.
- **Result:** no current UDP or NIC drops; host handles ~50k packets/s in and
  ~307k/s out. Several destinations had failed ARP.
- **Decision:** removed dead destinations; set NIC `rx-usecs` 8 → 0 (no
  measurable CPU cost). Skipped a NIC ring-size change because it would flap
  the link.

## North star and tooling

- **What:** p99 fan-out completion latency, measured from kernel packet
  timestamps, with guardrails for delivery, duplicates and CPU per send.
- **Tooling:** `fanout-bench` (branch `fanout-bench`): a passive production
  probe, an isolated lab that replays recorded traffic, and a run comparison
  with a strict "every run beats every run" rule.
- **Why it matters:** the earlier ~117 µs figure in `optimization.md` only
  counted time after packets reached the proxy, as a mean. It hid most of the
  real latency.

## First production baseline (port 23998)

- **Result:** p99 6.2 ms, p50 757 µs. One destination (`127.0.0.1:20300`)
  had no listener and was the slowest.
- **Change:** removed it → p99 3.1 ms, p50 213 µs. Every other destination
  got faster too.
- **Decision:** dead destinations are a recurring cost; check every instance.

## CPU sleep states (C2) — ruled out

- **Hypothesis:** waking cores from deep sleep costs ~30 µs per thread
  hand-off.
- **Result:** 4 vs 4 alternating runs with C2 on/off: no difference
  (first destination p50 87 vs 88 µs). Confirmed C2 was really disabled.
- **Decision:** left C2 enabled; look elsewhere.

## Profile of the forwarder path

- **Result:** biggest cost is the coordinator waking the 15 destination
  workers one by one (65–130 µs per shred). Each thread hand-off costs
  ~10–13 µs; each send 4–8 µs, mostly 1 packet per send. Kernel receive path
  is only 2–8 µs.
- **Decision:** the design must remove the per-shred wakeups and/or make
  each copy cheaper.

## Queueing identified

- **Result:** with little recent traffic, delivery to all destinations takes
  ~70 µs (p50). Under normal load (86% of shreds) it is ~4.5× slower at p50
  and 5–8× at p99.
- **Decision:** the target is capacity, not just per-shred speed: the
  forwarder must finish a shred well before the next one arrives.

## Lab baseline

- **Result:** 5 runs, very consistent (p99 13.7–14.9 ms), but ~5× slower
  than production.
- **Likely cause:** the forwarder's ~24 threads share only 4 cores in the
  lab.
- **Decision:** calibrate the lab with more cores before comparing
  candidates.
