# Chapter 7 — 2026-11-04

**Day summary:** failover design for one busy-looping proxy behind kernel
dedup: a primary that gets every shred and an idle standby that takes over
at the next packet while the primary is down or restarting (built, not yet
tested on Fra).

## One proxy plus a standby, chosen per packet in the kernel (built)

- **Plan (operator):** dedup receives on both source ports and passes every
  first copy to the primary proxy on 23998 (listen, dispatch and send
  threads busy-looping on pinned cores). A second proxy with the same
  destinations, unpinned and without busy loops, idles at ~0% CPU on its
  own port and gets the shreds only while 23998 has no socket. On Fra the
  standby is blockrazor's existing proxy on 23999 (stock settings), so no
  new service is needed.
- **Built:** `dedup.sh` takes `STANDBY_PORT=s`. For each first copy, dedup
  checks for a socket on the target port (`TO_PORT`); if none, it checks
  `s`, and if one is there it rewrites the destination port to `s` (same
  checksum update as `TO_PORT`). If neither has a socket, the copy passes
  untouched and is not recorded (fail-open, chapter 6), so another
  source's later copy can still get through. New counter "to standby".
  The standby port need not be a source port.
- **Cost:** the second socket lookup only runs while the primary is down.
  In normal operation it is the one lookup per first copy (~0.1 µs,
  estimate; `dedup.sh cost` measures it).
- **Why not the alternatives:** a same-port `SO_REUSEPORT` standby needs a
  `sk_reuseport` BPF program plus proxy changes to prefer the primary;
  falling back to blockrazor's copies (fail-open alone) costs 13–38 ms per
  shred and needs a second proxy anyway once everything goes to 23998.
- **Still lost on a primary restart:** shreds already inside the old
  process (its socket buffer and internal channels) when it exits:
  microseconds' worth with busy loops. Not covered: a primary that is
  alive but hung (socket open, nothing read); next step is a watchdog.
- `dedup-failover-test.sh` gained 3 cases (standby port 41003): all up →
  primary; primary down → standby; both down → the other source's port.
- **Fra: failover test passed (7/7); standby filter live** (`TO_PORT=23998
  STANDBY_PORT=23999`, both proxies still on their previous configs). First
  10 s: 41,215 first copies (~4.1k/s), 3.1 duplicates dropped per shred,
  0 errors; "to standby" and "no forwarder" 0, as expected with both up.
  1,495 first copies (3.6%) were rewritten from 23999 in those 10 s, but
  only 139 in the next ~367k (0.04%): right after an attach the map is
  empty, so blockrazor's late copies of shreds everstake had already
  delivered count as first again (a one-off burst of repeats downstream on
  every attach, not steady state).
- **Live failover drill: nothing lost.** Everstake's proxy restarted with
  the busy-loop config (11:46 UTC). During the restart 2,751 first copies
  went to the standby (~0.7 s of traffic) and "no forwarder" stayed 0
  (that the counter stops once 23998 is back: to be confirmed).
- Busy-loop config running: one listen socket on 23998 (`NUM_THREADS=1`),
  listener pinned to CPU 15, dispatch pinned to CPU 14 at ~100% (spinning,
  as designed), 23 send shards. No errors.

## One busy-looping proxy behind dedup + standby: first run

- Config: everstake proxy gets every first copy (`TO_PORT=23998`,
  standby 23999), `NUM_THREADS=1`, listener pinned to CPU 15 with
  `SO_BUSY_POLL` 50 µs (still blocks), dispatch pinned to CPU 14 and
  spinning (100% of that CPU), 23 send shards with balanced bond ports
  (sleep until woken, unpinned).
- 1 × 60 s (`fra-spin`): completion **p50 87 µs, p90 339, p99 1,280 µs**,
  p99.9 1.7 ms, max 2.0 ms; delivery 100%, 0 duplicate sends.
- vs `fra-shards-23` (1 run, p50 114, p90 464, p99 1,635): **p50 −24%,
  p90 −27%, p99 −22%**. Caveat: lighter traffic (3.2k vs 4.3k shreds/s),
  which by itself flatters the tail. Pending: 4 more runs.
- First copy out: p50 better (47 vs 57 µs) but **p99 worse (431 vs
  238 µs)**. Not yet explained; hypothesis: in bursts the dispatcher
  wakes up to 23 sleeping senders per batch, serially, and that work now
  sits on one thread.
- CPU 21.1 µs per send, of which the spinning core is ~60 s per 60 s
  run; without it ~7.8 µs per send, as before.
- Next (operator asked for all three loops spinning): a spinning
  listener (new non-blocking receive loop) and senders that spin ~50 µs
  before sleeping (no wake-up in bursts, idle between them); spinning all
  23 senders permanently would take 23 of 32 CPUs.
- **Confirmed over 5 runs each** (`fanout-measure compare`, vs
  `fra-shards-23`, 5 runs): completion **p99 median 1,364 µs vs 1,635
  (−16.6%), verdict IMPROVED** (every spin run beat every shards-23 run);
  p50 median 97 vs 126 µs (−22.5%) and first-copy p50 54 vs 60 µs
  (−10%), both with overlapping run ranges (not significant). Delivery
  100%, 0 duplicates. Traffic 3.4–3.9k shreds/s in the spin runs.
- First-copy p99 stays worse in every spin run (414–521 µs vs 238 in the
  shards-23 run shown): the open question above.
- Built (not compiled locally, not run): `--send-spin-us` /
  `SEND_SPIN_US`. Unpinned senders poll their queue that long after each
  batch before sleeping; a polling receiver isn't parked, so the
  dispatcher's hand-off needs no wake-up during a burst. Also queued:
  8 pinned, always-spinning senders (operator's idea; predicted worse
  tail, since 8 senders give ~80k shreds/s of capacity, about the burst rate).

## 8 pinned, always-spinning senders: first copy faster, completion slower (1 run)

- 12:01 UTC, `SEND_SHARDS=8 SEND_CORES=6-13`, rest as `fra-spin`
  (dispatch spinning on 14, listener on 15). Restart covered by the
  standby: 4,224 shreds via 23999 (~1 s), "no forwarder" 0.
- 1 × 60 s (`fra-spin-8`): completion **p50 158 µs, p90 644, p99
  1,448 µs**; first copy **p50 40** / p99 406 µs; delivery 100%,
  0 duplicates; ~3.6k shreds/s.
- vs `fra-spin` (5 runs, medians p50 97, p99 1,364; ranges 87–115 and
  1,280–1,464): **p50 +63% (outside the range), p90 worse, p99 at the top
  of the range**; first-copy p50 better (40 vs 54 µs).
- Reading: spinning senders save the wake-up (~10–15 µs on the first
  copy), but each sender serves ~3 destinations in turn, so the rest of a
  shred's copies wait behind them: the 3/6-shard pattern again, milder.
  As predicted, capacity and serial sends outweigh wake-ups. CPU ~9 full
  cores (543 s of CPU per 60 s). Not pursued.

## 23 senders that spin 50 µs before sleeping: best so far (1 run)

- 12:05 UTC, `SEND_SPIN_US=50` added to the `fra-spin` config (23
  unpinned senders). Restart via the standby: 3,735 shreds (~0.8 s),
  "no forwarder" 0.
- 1 × 60 s (`fra-spin-send50`): completion **p50 74 µs, p90 298, p99
  1,135 µs**, p99.9 1.6 ms; first copy p50 41 / p99 493 µs; ~4.7k
  shreds/s (busiest run of the day).
- vs `fra-spin` (5 runs; p50 87–115, p99 1,280–1,464): **p50, p90 and
  p99 all below the whole range of the spin runs**, at higher load. First
  copy p50 as fast as 8 always-spinning senders (41 vs 40 µs), while
  keeping 23-way parallelism. First-copy p99 unchanged (still ~400–500).
- CPU ~2.5 cores in all (153 s per 60 s run), of which ~1 is the
  spinning dispatcher; ~14.5 µs per send otherwise vs ~7.8: the senders'
  polling costs ~0.7 core at this load.
- Guardrail note: one shred (of 278,592) was not sent at all ("missing
  23" = all 23 copies of one shred). Every earlier run had 0 missing;
  possibly a capture-edge effect, to be watched in the next runs.
- **Confirmed over 5 runs** (vs `fra-spin`, 5 runs): completion **p50
  74 vs 97 µs (−24%), IMPROVED**; first copy p50 41 vs 54 µs (−23%),
  IMPROVED; p99 1,221 vs 1,364 µs (−10.5%), ranges overlap.
- **But shreds were lost:** 3 of 5 runs had shreds not sent to any
  destination (1, 1 and 30 shreds; 99.986% delivery in the worst run).
  The compare's delivery guardrail uses the median run and missed it.
  The 30-shred run had 49 `UdpRcvbufErrors` (box-wide; 0 in every other
  run), no tcpdump drops: the listen socket overflowed. Dedup had already
  dropped the other sources' copies, so those shreds were gone.
  The two single-shred losses had no counter: unexplained.
- Hypothesis: the 23 senders are unpinned and now spin, so the scheduler
  can put them on CPU 14/15 next to the spinning dispatcher and the
  listener; a stalled listener overflows its socket in a burst. Not
  kept as is; rollback to `fra-spin` recommended.
- Built: with `--recv-core`/`--dispatch-core` set, every other proxy
  thread is kept off those CPUs and their SMT siblings (process affinity
  set before any thread starts); `--recv-buffer-bytes` sets the listen
  socket's buffer (`SO_RCVBUFFORCE`) for more headroom in bursts.
