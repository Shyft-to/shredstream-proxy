## Fra rollout: plan

- **Why:** v1 (`shred-kfan.service`) runs on the first server (Ams) only.
- **Plan:** baseline with the proxies as they are → deploy v1 per
  `fanout/deploy/README.md` → benchmark again, same method.
- **Method:** box probe (`probe.sh box PORTS 60`), 6 runs 10 min apart
  before and after; `fanout-measure compare`, metric completion p99. Same
  method as Ams's before/after (321 µs / 5.4 ms → ~82 µs / ~245 µs), so the
  regions compare directly. Kernel CPU after the switch from
  `kfan.sh cost 20` (the probe counts only the proxies' CPU).
- **Limitation:** runs before and after are not interleaved (unlike the Ams
  A/B), so a load change between the two hours shows up as a latency
  change; compare the shred count per 60 s window.
- **Decision:** baseline taken on Fra as found: no `rx-usecs` change, no
  removal of dead destinations, so the comparison measures kfan alone.
  Problems found are noted and fixed afterwards.
- Commands are run on Fra by hand from the `fanout-opt` branch.

## Survey for new servers (`fanout/deploy/survey.sh`)

- Read-only, needs no config: proxies (ports, destinations, CPU, dynamic
  discovery), every destination's cached neighbour state and local
  listeners, the device the shreds arrive on (3 s passive capture), bond
  ports / driver / speed / `rx-usecs`, anything already attached. Prints a
  draft `kfan.env`; the example file's destinations are Ams's.
- Not yet run on Linux; Fra is its first run.

## Fra survey: v1 does not fit as is

- **Server:** fra-shred-proxy, kernel 6.8.0-50, 32 CPUs; `bond0` (802.3ad)
  over 2 × 10 Gb/s **ixgbe** ports (Ams: i40e), `rx-usecs` 1; private
  destinations on VLAN `bond0.3984`, public ones via a gateway on `bond0`.
  No tc or XDP programs attached.
- **Sources (4 proxies):**

| Port | Service | Destinations (listed / unique) | CPU | Traffic in 3 s |
|---|---|---|---|---|
| 23999 | blockrazor | 32 / 31 | 237% of a core | yes, both ports |
| 23998 | everstake | 29 / 27 | 73% | yes, one port |
| 7733 | doublezero | 29 / 27 (as everstake) | 0% | none |
| 20000 | shredstreams | 1 (127.0.0.1:20200) | 0% | none |

- **Differences from Ams that block v1:**
  1. **31 destinations**, kfan takes at most 16 on one CPU (more only as
     multi-CPU groups, ruled out on Ams: p99 ~3× worse).
  2. **Different destination lists per source:** blockrazor has 4 more than
     everstake (10.182.192.64:20200, :20300, 127.0.0.1:20200, :20400). kfan
     has one list for all ports and dedups across them, so those 4 would also
     get shreds that arrive first from everstake.
  3. **10.182.192.10:8002 has no MAC** (neighbour INCOMPLETE): kfan does not
     start with it in the list.
- **Dead or wasteful today:** 127.0.0.1:20400 has no listener; .10 copies
  never leave the box; blockrazor lists 1 destination twice, everstake 2
  (each sent twice). Left as they are for the baseline.
- **Baseline method adjusted:** the probe counts a shred toward completion only
  once every destination has it, so with .10 in the list no shred would
  count. `probe.sh box` takes `DESTS=` now; the Fra baseline is judged on
  the **26 live destinations both active proxies share** (ports 23998,
  23999). Runs: 5 × 60 s, 10 s apart (one stretch of traffic, not spread
  over an hour; the kfan side the same way).
