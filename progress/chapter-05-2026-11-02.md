## Fra rollout: plan

- **Why:** v1 (`shred-kfan.service`) runs on the first server (Ams) only.
- **Plan:** baseline with the proxies as they are → deploy v1 per
  `fanout/deploy/README.md` → benchmark again, same method.
- **Method:** box probe (`probe.sh box PORTS 60`), 6 runs 10 min apart
  before and after; `fanout-measure compare`, metric completion p99. Same
  method as Ams's before/after (321 µs / 5.4 ms → ~82 µs / ~245 µs), so the
  regions compare directly. Kernel CPU after the switch from
  `kfan.sh cost 20` (the probe counts only the proxies' CPU).
- **Limitation:** runs before and after are not interleaved (unlike the Ams
  A/B), so a load change between the two hours shows up as a latency
  change; compare the shred count per 60 s window.
- **Decision:** baseline taken on Fra as found: no `rx-usecs` change, no
  removal of dead destinations, so the comparison measures kfan alone.
  Problems found are noted and fixed afterwards.
- Commands are run on Fra by hand from the `fanout-opt` branch.

- Fra needs 25 destinations on one CPU (24 shared + 127.0.0.1:20200),

  with their proxies). One list for both ports (union): both sources carry

- `fanout/deploy/kfan.env.fra`: Fra's config (dead destinations left out).
- **Expectation (hypothesis):** ~25 × 1.7–1.9 µs ≈ 45 µs of sending per
  shred, vs ~26 µs on Ams, at about half Ams's shred rate. Bursts still
  land on one CPU, so the tail is the open question (multi-core: below).

## Multi-core kfan: options (no XDP)

- **Constraint:** v1 loads nothing into the NIC driver (no XDP; decided in
  chapter 4 after the refused-copy incidents). Fra runs the same tc-only
  kernel fan-out as Ams.
- **Why one CPU:** the NIC picks a receive queue (and so a CPU) per flow;
  each source is one flow, so all of everstake's shreds land on one CPU and
  a burst's fan-outs queue behind each other there.
- **Already tried (Ams, chapter 2): split the destinations over CPUs**
  (`KFAN_GROUPS`, tc carriers re-injected with packet steering). p50 92 →
  68 µs but p99 268 → 756 µs: the other CPUs start only after the receiving
  CPU finishes its whole receive batch, including sending its own group for
  every packet in it.
- **Remaining tc-only variant (untested): split the shreds over CPUs** with
  the same carrier mechanism: the receiving CPU only dedups and hands each
  whole shred to one of N CPUs (no sending itself), so its batch ends much
  sooner. Same batch-end hand-off as the failed variant, so likely limited.
- **Decision:** Fra gets single-CPU v1 (as Ams). Multi-core only if Fra's
  measured tail calls for it, and then as an A/B experiment.
