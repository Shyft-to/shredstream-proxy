## Fra rollout: plan

- **Why:** v1 (`shred-kfan.service`) runs on the first server (Ams) only.
- **Plan:** baseline with the proxies as they are → deploy v1 per
  `fanout/deploy/README.md` → benchmark again, same method.
- **Method:** box probe (`probe.sh box PORTS 60`), 6 runs 10 min apart
  before and after; `fanout-measure compare`, metric completion p99. Same
  method as Ams's before/after (321 µs / 5.4 ms → ~82 µs / ~245 µs), so the
  regions compare directly. Kernel CPU after the switch from
  `kfan.sh cost 20` (the probe counts only the proxies' CPU).
- **Limitation:** runs before and after are not interleaved (unlike the Ams
  A/B), so a load change between the two hours shows up as a latency
  change; compare the shred count per 60 s window.
- **Decision:** baseline taken on Fra as found: no `rx-usecs` change, no
  removal of dead destinations, so the comparison measures kfan alone.
  Problems found are noted and fixed afterwards.
- Commands are run on Fra by hand from the `fanout-opt` branch.

## Survey for new servers (`fanout/deploy/survey.sh`)

- Read-only, needs no config: proxies (ports, destinations, CPU, dynamic
  discovery), every destination's cached neighbour state and local
  listeners, the device the shreds arrive on (3 s passive capture), bond
  ports / driver / speed / `rx-usecs`, anything already attached. Prints a
  draft `kfan.env`; the example file's destinations are Ams's.
- Not yet run on Linux; Fra is its first run.
