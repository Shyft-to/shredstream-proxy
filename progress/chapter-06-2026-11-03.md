## geyserbench: kfan adds ~1 ms at p50

- **Observation (operator):** geyserbench, gRPC streaming latency of one of
  our dedicated nodes vs richat instances: with shred-kfan enabled, p50
  is ~1 ms **worse** than with the proxies.
- **Hypothesis A (to rule out first):** the dedicated node is fed through
  127.0.0.1:20200, which was not in kfan's 23 destinations, so under kfan
  it got no shreds from 23998/23999.
- **Hypothesis B:** a transaction is visible only once the node has the
  whole batch (FEC set, ~32 shreds) that carries it, so what matters is the
  burst's *last* shred at each destination. kfan sends serially on one CPU,
  ~32 µs per shred (23 copies), i.e. ~1 ms for a 32-shred burst, and every
  destination gets the burst's last shred ~1 ms late. One CPU sustains
  ~31k shreds/s; ~45% of shreds arrive at > 64k/s. The proxies send per
  destination in parallel (one thread each, a burst in one batch send:
  ~150–300 µs). The probe cannot see this: under kfan the rest of a burst
  waits in the NIC ring before the arrival stamp (chapter 5).
- **Lesson:** per-shred completion p99 is not what geyser consumers feel;
  per-destination FEC-set completion is closer.
- **Next:** confirm which destination the dedicated node receives on;
  measure per-destination FEC-set completion (first shred of the set
  arrives → last copy of the set leaves for that destination) for kfan
  and the proxies. The first shred of a burst is picked up at once, so
  the ring blind spot does not hide it.

|---|---|---|
| Completion p50 | **125 µs** | 176 µs |
| First copy p50 | **58 µs** | 135 µs |
| Completion p99 | 2,789 µs | **373 µs** |
| p99.9 / max | 5.4 ms / 29 ms | **~0.43 / ≤ 0.55 ms** |
| CPU | ~2.6 cores | **~0.13 core** |
| Load | ~3.5k shreds/s | ~4.4k shreds/s |

- **Established (pending more runs):** the proxies win the typical shred,
  kfan wins the tail. The proxies' arrival stamps are accurate (receiving
  CPU idle); kfan's miss the NIC ring wait, so the true p50 gap is larger.
- Why: the proxies send per destination in parallel (one thread each), and
  each destination gets every shred from **both** proxies, the faster copy
  counting. kfan sends all copies serially on one CPU.
- **Correction:** the ~2.3 copies per send in the baseline were mostly the
  two proxies both forwarding every shred, not duplicate list entries
  (still 2.28 after the lists were cleaned).
- A ~50–80 µs per-shred p50 gap does not explain geyserbench's +1 ms by
  itself; hypotheses A (20200) and B (burst completion) still open.
- Same two destination groups as before (8 with p99 ~0.26–0.35 ms, 15 with
  ~1.7–2.0 ms); a 29 ms stall on every destination at once.

## Target and plan

- **Target (operator):** p50 ≤ the cleaned proxies' (~125 µs) and p99
  < 300 µs.
- **Arithmetic:** ~45% of shreds arrive in bursts > 64k shreds/s; × 23
  copies × ~1.4 µs (kfan, no capture) ≈ 2 CPU-seconds per second during a
  burst. One CPU sustains ~31k shreds/s, so the last shred of a 32-shred
  burst waits ~0.5 ms: **p99 < 300 µs needs ≥ 2–3 CPUs in bursts or ~3×
  cheaper copies.** The proxies have the parallelism (good p50) but pay
  ~4–5 µs per copy in userspace (bursts collapse).
- **Options, cheapest first:**
  1. Parallelism from the existing duplicates: each shred arrives ~4 times;
     if the copies are distinct flows, NIC flow rules can put each on its
     own queue/CPU (configuration, no driver code); the first free CPU wins
     the dedup and fans out. Already seen: blockrazor first for 2–4% while
     everstake's CPU is busy. Depends on flows and the lag between copies.
  2. Cheaper copies: IOMMU passthrough (reboot), a bypass-capable qdisc on
     the NIC ports; measured with `kfan.sh cost`. Likely 20–40%.
  3. Latency-sensitive destinations first in the table (copies leave in
     order, ~1.4 µs apart).
  4. If 1 is not enough: whole-shred hand-off to other CPUs in tc (receiving
     CPU only dedups and hands off); untested, code change.
- **Measurement:** per-destination FEC-set completion (closer to what geyser
  sees), the remaining `fra-proxies-clean` runs as reference, and the true
  arrival process from the proxy-era captures to check a design against
  real bursts (the probe cannot see kfan's NIC ring wait).
- **Next:** read-only data: source flows per port, RX queue per flow,
  IOMMU state, NIC qdiscs.
