# Chapter 2 — 2026-10-15

**Day summary:** switched candidate testing from the lab to live production
traffic, using alternating A/B runs; started our own forwarder,
`shred-fanout`, on branch `fanout-opt`.

## Test on production instead of the lab

- **Why:** the lab baseline is ~5× slower than production, so it could rank
  candidates wrongly; production is the ground truth.
- **How:** `ab.sh` takes over one instance (23998), stops its systemd
  service, alternates the baseline and candidate binaries with the same
  arguments (10 s warmup + 10 s measurement each), and restarts the service
  at the end. Alternating cancels out traffic drift between runs.
- **Decision:** validate with an A/A run (baseline vs itself) first, then
  test `opt_1_1`. The lab stays for basic correctness checks of new
  prototypes before they touch live traffic.

## New forwarder: shred-fanout (branch `fanout-opt`)

- **Why:** a fresh design aimed at the measured bottlenecks, instead of the
  older `opt_1_1` experiment.
- **Design:** one receive thread busy-polls the socket (no wakeup per
  packet) and drops duplicates exactly; each unique shred goes once into a
  lock-free broadcast ring; 4 pinned sender threads each own a share of the
  destinations and send a shred to all of them in one `sendmmsg`. No locks or
  sleeping hand-offs on the path. Same command line as the proxy's
  `forward-only`, so it drops into `ab.sh`.
- **Cost:** 5 threads spinning at 100% CPU (receiver + 4 senders).
- **Status:** unit-tested (ring, dedup); not yet run on Linux.
- **Next:** A/B against the current proxy on 23998.

## First A/B: shred-fanout v1 is slower

- **Result (6 vs 6 alternating runs on 23998):** completion p50 439 vs
  195 µs and first destination p50 155 vs 87 µs, both **REGRESSED**;
  p99 median 7.96 vs 1.96 ms. Delivery 100%, no duplicates.
- **Hypothesis:** pinning spinning threads does not reserve the cores. Other
  instances' threads and kernel network work still get scheduled onto
  cores 12–16 and share them with spinners that never yield, so our threads
  sit switched out for milliseconds at a time.
- **Decision:** measure each thread's time waiting for a CPU (added to the
  probe) before changing the design.

## Profiling both forwarders: preemption ruled out

- **Result (1 profiled pair):** `shred-fanout` gets packets off the socket
  ~6× sooner (3.7 vs 21 µs) and hands them to senders ~6× sooner (19 vs
  117 µs). Its threads were almost never preempted (16 ms in 10 s) and
  barely waited for a CPU (17 vs 613 ms for the proxy). Yet completion p50
  was still 2× worse (535 vs 271 µs), and each `sendmmsg` call took 56 vs
  15 µs.
- **Conclusion:** the "switched out" hypothesis is rejected. About 100 µs
  per shred is lost in or around the send, after a sender picks up the
  shred.
- **Next:** check for queueing in `bond0`/VLAN devices and whether the
  slowdown follows particular senders or destinations.

## shred-fanout is fast when quiet, but runs out of send capacity in bursts

- **Ruled out:** queueing in the network devices (`bond0` and the VLAN use
  `noqueue`).
- **Result:** the slowdown follows the senders: the sender with 3
  destinations had p50 ~185 µs, the three with 4 destinations ~410–480 µs.
  With little recent traffic, `shred-fanout` beats the proxy clearly (first
  destination p50 ~10 vs ~43 µs, completion ~33 vs ~74 µs); in dense bursts
  it is much worse (completion p50 1,066 vs 456 µs).
- **Finding:** 46% of shreds arrive in bursts of 32+ shreds per 500 µs
  (over 64k shreds/s while the burst lasts), much denser than assumed.
- **Hypothesis:** send capacity. Each copy costs ~4.6 µs of kernel work, so
  a sender with 4 destinations needs ~18 µs per shred, more than the ~15 µs
  between shreds in a burst. Bursts need ~4.4 cores of send work in total.
- **Next:** test with 8 senders. If confirmed, make each copy much cheaper
  (eBPF, or raw-frame sending with `AF_PACKET`) rather than add cores.

## 8 senders: capacity confirmed, but cores are not the answer

- **Result (3 vs 3 alternating runs):** first destination p50 20 vs
  100 µs (**IMPROVED**, 5× faster); completion p50 232 vs 228 µs (same);
  p99 4.0 vs 3.0 ms (overlapping). With 4 senders, completion p50 had been
  2.2× worse.
- **Conclusion:** send capacity limits `shred-fanout`. More senders help,
  but matching the baseline already takes 9 spinning cores: each shred needs
  15 copies × ~4.6 µs ≈ 70 µs of kernel send work, ~4.4 cores during bursts.
- **Decision:** cut the cost per copy instead of adding cores. Next: CPU
  profile of the send path to see where the ~4.6 µs goes.

## CPU profile of the send path; three sources, same destinations

- **Result:** in the proxy's CPU profile the per-copy kernel cost is spread
  across many layers: mitigation thunks ~4%, copying/allocation ~4.5%,
  UDP/IP ~3.5%, device layers ~3%, connection tracking ~1.8% (active
  because of a NAT table), routing ~1.5%, IOMMU ~0.9%. `shred-fanout`'s
  profile is dominated by its own idle spinning (senders mostly wait for
  bursts).
- **Conclusion (hypothesis):** kernel tuning would save only ~10–20% per
  copy; a 3× cut needs bypassing the UDP/IP stack.
- **New context:** the server runs 3 forwarders (ports 5544, 23997, 23998),
  one source each, all to the same 15 destinations.
- **Next:** measure how many shreds the 3 sources share. If most, merge the
  three into one deduplicating forwarder before optimising the send path.

## The three sources carry the same shreds

- **Result (10 s capture of all three ports):** 98.8% of shreds arrive on
  all three; one deduplicating forwarder would send 2.98× fewer copies.
  23997 delivers first 52.5% of the time, 23998 47.5%; 5544 never (12.3 ms
  behind at p50, 46 ms at p90), but it alone delivers ~1% of shreds.
- **Decision (pending confirmation that destinations need only one copy per
  shred):** merge the three forwarders into one that listens on all three
  ports and forwards each shred once, from the first source. Measure with a
  box-level north star: first arrival on any port → first copy leaving the
  box for each destination.

## Kernel dedup across sources; box-level north star

- **Confirmed:** destinations drop duplicates themselves, so forwarding one
  copy per shred (the earliest) loses nothing.
- **Built:** an eBPF filter on `bond0` ingress (`fanout/ebpf/dedup.bpf.c`)
  that lets only the first copy of each shred through, on whichever of the
  three ports it arrives, and drops the rest. The three forwarders stay
  unchanged; each simply forwards the shreds its source delivered first.
  Attach/detach is instant (`fanout/scripts/dedup.sh`).
- **North star moved to box level:** first arrival on any port → first copy
  leaving the box for each destination, across all forwarders. Needed
  because a per-forwarder view would report deduplicated shreds as missing.
- **Test:** `toggle.sh` alternates the filter off/on under live traffic.

## Kernel dedup A/B on production

- **Result (4 vs 4 alternating runs, box level, forwarders unchanged):**
  completion p50 280 → 191 µs (**IMPROVED**, −32%); first destination p50
  104 → 76 µs (**IMPROVED**, −26%); forwarder CPU ~7 → ~1.35 cores
  (**IMPROVED**, −81%); p99 median 4.46 → 2.59 ms (ranges overlap).
  Delivery 100%, copies per destination 3.08 → 1.00.
- **Filter cost:** 625 ns of kernel CPU per packet (~2.6% of one core); in
  10 s it passed 70k first copies, dropped 274k duplicates, no errors.
- **Next:** more pairs to settle p99; then deploy (attach at boot).

## Kernel dedup, 8 pairs; a delivery dip under investigation

- **Result (8 vs 8):** completion p50 258 → 169 µs (**IMPROVED**, −35%);
  first destination p50 94 → 67 µs (**IMPROVED**, −29%); CPU −80%
  (**IMPROVED**); p99 3.88 → 2.23 ms (−42%, ranges overlap, same as with
  4 pairs).
- **Delivery dipped to 57–94% in the first 4 pairs on both sides**, then
  ~100%. Not the filter (both sides), not a destination outage (every
  destination got the same shreds), not forwarder restarts (all running
  since 12:22, `NRestarts=0`), not socket overflow (0 UDP receive errors).
  In those runs ~2× the usual number of distinct shreds arrived, decaying
  back to normal over ~3 minutes; none of the extra ones were forwarded.
- **Hypothesis:** a source re-sent older shreds that the forwarders had
  already forwarded minutes earlier; their own dedup (5 min memory) dropped
  them correctly, but the 10 s probe never saw the originals and counted
  them as missing. The probe now reports the slot age of incomplete shreds
  and which port they came from, and keeps captures when delivery < 99.9%.
- **Side finding:** the old dead IPs (`.15`, `.23`, `.24`, `.26`, `.37`,
  `.72`, `.88`) still show `FAILED` in the neighbour table, so some process
  on the box still sends to them.

## Kernel dedup proven on all metrics

- **Result (8 vs 8 alternating runs, clean delivery):** completion p99
  5.45 → 2.43 ms (**IMPROVED**, −55%); p50 321 → 185 µs (**IMPROVED**,
  −42%); first destination p50 113 → 73 µs (**IMPROVED**, −36%); CPU
  ~8.0 → ~1.6 cores (**IMPROVED**, −80%). Every "on" run beat every "off"
  run on all four. Delivery 99.999–100%, no duplicates.
- **The delivery dip did not recur.**
- **Decision:** deploy the filter permanently (systemd service, instant
  rollback by stopping it).

## Three shred-fanout instances vs three proxies

- **Result (6 vs 6, box level):** with the kernel filter on, `shred-fanout`
  ×3 was not better (p99 5.94 vs 2.29 ms, p50 238 vs 176 µs, both
  overlapping) at ~15 vs ~1.7 cores (**REGRESSED**). With the filter off,
  p99 **REGRESSED** (8.11 vs 4.68 ms).
- **Hypothesis:** per instance, the proxy sends a shred's 15 copies through
  15 parallel threads; `shred-fanout`'s 4 senders send ~4 copies each in
  series and still queue in bursts. The per-copy kernel cost (~4.6 µs) is
  the limit for every userspace design.
- **Next:** single `shred-fanout` on all three ports (4 and 8 senders); then
  consider fanning out in the kernel (clone each first copy to all
  destinations in the same eBPF program).

## One shred-fanout for all three ports (8 senders, kernel dedup on)

- **Result (6 vs 6, vs 3 proxies + kernel dedup):** first destination p50
  11 vs 75 µs (**IMPROVED**, −85%); completion p50 75 vs 181 µs
  (**IMPROVED**, −58%); p99 unchanged (2.67 vs 2.57 ms); CPU ~9 vs ~1.8
  cores (**REGRESSED**). (An earlier attempt at 13:32 accidentally ran the
  old script, i.e. three instances on the same 9 cores; discarded.)
- **Conclusion:** the typical shred gets much faster, but the tail is set by
  something both setups share; **hypothesis:** the per-copy kernel send cost
  during bursts.
- **Delivery was low on both sides** (~90–92%), the same unexplained episode
  as before; captures were kept this time.

## Kernel fan-out built

- **What:** `fanout/ebpf/kfan.bpf.c`: dedup as before, then the first copy
  of each shred is cloned straight to every destination from the receive
  path (headers rewritten per destination: VLAN device for private
  destinations, gateway MAC for the public one, loopback for local), and the
  original dropped. No socket, syscall, thread, routing or firewall per copy.
  Fail-open: empty table or error → the forwarders (kept running) handle it.
- **Next:** correctness in the lab, then A/B on production against
  3 proxies + kernel dedup (`kfan-ab.sh`).

## Kernel fan-out: lab correctness test passed

- **Result (30 s of recorded 23998 traffic, 15 destinations, lab):**
  delivery 100% (3.5 M copies), no duplicates, no copies refused;
  completion p50 19 µs, p99 29 µs; first destination p50 1.9 µs; no
  userspace CPU. Latency flat across load levels (no queueing).
- **Cost per copy ~1.2 µs** (each destination ~1.2 µs after the previous
  one), vs ~4.6 µs through a UDP socket.
- A second replay of the same capture was (correctly) dropped as duplicates
  by the kernel's dedup table; the replayer now salts each run.
- **Next:** A/B on production vs 3 proxies + kernel dedup.

## Kernel fan-out on production: p99 −87%

- **Result (6 vs 6, box level, vs kernel dedup + 3 proxies):** completion
  p99 2,354 → 313 µs (**IMPROVED**, −87%), very stable (292–322 µs across
  runs); p50 137 → 89 µs (**IMPROVED**, −35%); first destination 61 → 51 µs
  (**IMPROVED**, −17%). Kernel counters: every forwarded shred got all 15
  copies, none refused.
- **Delivery low on both sides** (77.7% vs 82.1%), the shared, still
  unexplained episode; slot-age breakdown pending.
- **Hypothesis for the remaining ~90 µs p50 / ~300 µs p99:** the 15 copies
  are sent serially on the CPU receiving that source (~2.8 µs per copy
  through VLAN, bond and NIC driver), so that CPU saturates in dense bursts.
- **Next:** confirm delivery, measure kernel CPU cost, decide on deployment.
